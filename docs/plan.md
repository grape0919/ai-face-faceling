## 1. 제품 정의

**실시간 대화 API의 이벤트 스트림과 오디오를 입력으로 받아, 아바타 표정 프레임 스트림을 출력하는 미들웨어 라이브러리.**

```
[Realtime API 이벤트 + 오디오] → [AI FACE 엔진] → [ARKit 52 blendshape + 머리 자세, 60fps]
```

- 모델도, 아바타도 직접 제공하지 않는다. 둘 사이의 변환 계층만 담당한다.
- 의미 판단은 Jev(TypeSafe AI)에, 렌더링은 기존 아바타 생태계(VRM, Live2D, Unity 등)에 맡긴다.
- 핵심 자산은 표정 엔진: 판단값 + 립싱크 + 턴 상태 + 절차적 애니메이션을 **오디오 재생 타임라인 위에서** 합성하고 보간하는 코드.

### 대상 사용자
- 음성 AI 제품에 얼굴을 붙이고 싶은 개발자
- 아바타 챗봇, 가상 상담원, 교육용 튜터, 게임 NPC 제작자

### 차별점
1. **텍스트 의미를 읽는다.** 오디오만 보는 방식은 같은 톤의 사과와 농담을 구분하지 못한다.
2. **들을 때도 표정이 있다.** 사용자 발화를 실시간으로 받아 반응 표정을 만든다.
3. **API 중립, 아바타 중립.** 입력은 어댑터, 출력은 ARKit 52 표준.

### 동작 수준 (v4 신설)
라이브러리는 갖춰진 구성 요소에 따라 세 수준으로 동작한다. 상위 수준의 구성 요소가 실패하면 한 단계 아래로 자동 강등한다.

| 수준 | 필요한 것 | 제공하는 것 |
|---|---|---|
| **L0** 오디오만 | AI 음성 오디오, 턴 이벤트 | 립싱크, 턴 상태 표정(듣기·생각·말하기), 깜빡임·시선·미세 움직임 |
| **L1** + 의미 | L0 + AI 발화 텍스트 + 분석기(Jev 또는 인라인 태그) + 프록시 서버 | AI 발화의 정서·의도 표정 |
| **L2** + 듣기 반응 | L1 + 사용자 발화 부분 전사(API 제공 또는 별도 STT) | 사용자가 말하는 동안의 반응 표정 |

- L0만으로도 쓸 만해야 한다. 외부 키 없이 붙일 수 있는 진입점이자, 모든 장애의 최종 대체 동작이다.
- 개발 순서도 L0 → L1 → L2를 따른다.

### 경쟁 및 인접 도구
| 도구 | 방식 | 우리와의 관계 |
|---|---|---|
| NVIDIA Audio2Face 계열 | 오디오 → blendshape + 감정 추정 | 립싱크·음성 톤은 강함, 텍스트 의미는 못 읽음. 결합 가능한 립싱크 레이어 후보 |
| 대화형 아바타 영상 서비스 | 서버에서 얼굴 영상 생성·스트리밍 | 완성형 제품. 우리는 아바타·렌더러를 고객이 고르는 라이브러리 |
| Hume EVI | 음성 대화 + 음성 감정 점수 | 입력 소스 후보 |

## 2. Jev 조사 요약 (설계에 영향을 주는 사실만)

| 항목 | 내용 |
|---|---|
| 방식 | 요청-응답 REST. `POST https://api.typesafe.ai/v1/systemone`. 스트리밍 입력·상태 유지 세션 없음 |
| 질문 타입 | Noul(예/아니오 확률 하나, confidence 없음), Choice(선택지 + 분포 + confidence), Score(2~10단계 확률 가중 평균 + 분포 + confidence) |
| 병렬 질문 | 한 요청의 질문들은 같은 state에 대해 병렬 평가 |
| 지연 | 공식 70~500ms, 보통 약 100ms. **미국 서부 기준** |
| 가격 | 입력 $0.042 / 1M 토큰, 출력 무료 |
| 한계 | state + 질문 1개 ≤ 약 32k 토큰. 크고 잡음 많은 state에서 정확도 저하. 조직별 rate limit(수치 미확인) |
| SDK | `@typesafe-ai/sdk` (Node), `typesafe-sdk` (Python), Vercel AI SDK |

**설계 결론**
- 비용은 제약이 아니다.
- 상태 유지형이 아니므로 누적과 구간 관리는 클라이언트가 한다.
- AI 발화는 응답 중반부터 텍스트가 재생보다 앞서므로 Jev 지연이 흡수된다. 지연이 결정적인 곳은 **응답 첫 구절**과 **사용자 발화 반응**이다.
- 프록시 서버는 Jev에 가까운 리전(미국 서부)에 둔다. 한국에 두면 서버 → Jev 구간에서 태평양 왕복이 한 번 더 생긴다.

### 지연 예산 (사용자 발화 반응, 한국 사용자 기준 추정)

| 구간 | 추정 |
|---|---|
| STT 부분 전사 | 300~500ms |
| 브라우저 → 프록시(미국 서부) → Jev → 복귀 | 250~500ms |
| 엔진 보간 시작까지 | 1프레임 |
| **합계** | **약 0.6~1.0초** |

- 모두 추정치이며 Phase 0에서 실측한다. 목표는 p95 1초 이내.

### 설계 원칙
1. **표정은 재생 타임라인 위에 예약한다.** 기준은 이벤트 도착 시각이 아니라 해당 단어가 들리는 시각이다.
2. **이벤트 도착과 렌더링 분리.** 이벤트는 목표값을 예약·갱신만 하고, 60fps 루프가 보간한다.
3. **분석기, 립싱크, STT, 전송 방식은 모두 플러그형.**
4. **엔진은 브라우저, 비밀은 서버.**
5. **아래 수준은 항상 살아 있다.** 상위 수준이 멈춰도 L0는 계속 동작한다.

### 전송 방식 비교 (Phase 0에서 결정)

| | WebSocket | WebRTC |
|---|---|---|
| 오디오 수신 | 청크 단위 이벤트, 클라이언트가 직접 재생 | 미디어 트랙, 브라우저가 재생 |
| 재생 위치 | 클라이언트가 정확히 앎 | 추정해야 함 |
| 텍스트 ↔ 오디오 대응 | 전사 델타 도착 시점의 누적 오디오 길이를 앵커로 사용 가능 | 말하기 속도 추정에 의존 |
| 끼어들기 | 클라이언트가 재생 중단과 잘린 위치 통보를 직접 처리 | 서버·브라우저가 처리 |
| 음성 품질·지연 | 재생 버퍼, 지터 처리를 직접 구현 | 내장 |
| 구현량 | 많음 | 적음 |

- 위 특성은 현재 이해 기준이며 Phase 0에서 실제 동작으로 확인한다.
- 결정 기준: **표정 시각 오차 p95**. WebRTC 추정 방식이 목표(300ms)를 만족하면 구현이 단순한 WebRTC, 아니면 WebSocket.
- 어댑터 인터페이스는 두 방식 모두 "재생 위치를 질의할 수 있다"는 계약만 요구한다.

## 4. 발화 타임라인

### 4.1 문제
실시간 API는 텍스트와 오디오를 재생 속도보다 빠르게 생성한다. 도착 즉시 표정을 바꾸면 아직 말하지 않은 문장의 표정이 먼저 나온다. 그리고 응답이 끝나기 전에는 전체 길이를 알 수 없으므로, 추정은 진행 중에 계산 가능해야 한다.

### 4.2 진행형 추정
구간의 예상 재생 시작 시각을 다음 순서로 구한다. 위쪽 정보가 있으면 그것을 쓴다.

1. **단어 타임스탬프** (외부 TTS 경로): 그대로 사용.
2. **오디오 앵커** (WebSocket 경로): 전사 델타가 도착한 시점까지 받은 오디오의 누적 길이를 그 텍스트 위치의 재생 시각 근사값으로 기록한다.
3. **말하기 속도 추정** (WebRTC 경로 및 공통 대체): `구간 시작 시각 = 발화 시작 시각 + 앞선 글자 수 ÷ 말하기 속도`.
   - 말하기 속도 초기값은 Phase 0에서 측정한 음성별 평균(글자/초).
   - 응답이 진행되는 동안, 문장 경계와 오디오의 쉼 구간(에너지 급감)이 대응될 때마다 속도와 오프셋을 다시 맞춘다.
   - 응답이 끝나면 실제 총 길이로 그 음성의 속도 평균을 갱신해 다음 응답에 쓴다.

- 예약된 시각은 보정이 일어날 때마다 아직 재생되지 않은 구간에 한해 다시 계산한다.
- 분석 결과가 재생 시각보다 늦게 도착하면 즉시 적용한다(폐기하지 않음).

### 4.3 응답 첫 구절: 시작 표정 선점
응답 시작 직후에는 텍스트와 오디오가 거의 동시에 오므로 첫 구간의 분석 결과는 항상 늦는다.

- 사용자 턴이 끝나는 순간, 마지막 사용자 발화 분석값을 반응 매핑(5.5)에 통과시켜 **시작 표정**을 정해 둔다.
- 응답 재생이 시작되면 시작 표정을 감정 레이어의 목표값으로 건다.
- 첫 구간의 분석 결과가 도착하면 그 값으로 부드럽게 넘어간다.
- L1(사용자 분석 없음)에서는 중립에 가까운 "말 시작" 프리셋을 쓴다.
- 첫 구간은 길이 하한 없이 가능한 한 빨리 끊어 보낸다(첫 쉼표나 8~10자).

### 4.4 끼어들기
사용자 발화 시작 또는 응답 취소 이벤트를 받으면:
1. 아직 재생되지 않은 구간의 예약 표정을 모두 취소한다.
2. AI 발화 큐의 대기 요청을 비우고, 진행 중 요청의 결과는 버린다.
3. 턴 상태를 listening으로 전환하고 짧은 "멈칫" 표정을 넣는다.

### 4.5 오차 측정 방법
- 녹화된 세션의 AI 음성을 오프라인 음성 인식에 넣어 **단어별 타임스탬프**를 얻고 이를 정답으로 삼는다.
- 구간 시작 단어의 정답 시각과 엔진이 표정을 적용한 시각의 차이를 오차로 기록한다.
- 이 측정은 녹화·재생 하네스의 기능으로 자동화한다.

## 5. 분석기 호출 설계

### 5.1 큐 이원화

| | AI 발화 큐 (L1) | 사용자 발화 큐 (L2) |
|---|---|---|
| 목적 | 재생될 모든 구간의 표정 | 지금 이 순간의 반응 |
| 정책 | **순서 보장, 누락 없음** | **latest-wins** (대기 슬롯 1개) |
| 동시 요청 | 2~3개, 결과는 구간 순번으로 타임라인에 예약 | 1개 |
| 구간 생성 | **절 단위**: 쉼표·문장 경계, 또는 15~40자 중 먼저 오는 쪽 | 부분 전사 갱신 시마다 |
| 지연 민감도 | 첫 구간만 높음 | 높음 |

- 한국어 15~40자는 대략 3~7초 분량이다. 강조·질문처럼 순간에 붙는 표정이 어긋나지 않는 크기다.
- 전역 동시 요청 상한을 두고, 초과 시 사용자 큐를 우선한다. 상한 값은 Phase 0에서 확인한 rate limit으로 정한다.

### 5.3 질문 세트: 텍스트의 정서와 의도만 묻는다

> **2026-11-11 변경 (오프라인 실험에 적용).** 사용자 결정으로 방식을 바꿨다. 분석기에 정서·의도를 묻고 코드가 얼굴로 옮기는 대신, **Jev 가 얼굴 부위별 동작을 직접 고른다.** 부위 6개(눈썹, 눈, 시선, 볼·코, 입, 머리)마다 Choice 질문 하나, 표정 세기에 Score 질문 하나로 요청당 질문은 7개다. 선택지별 확률이 그대로 동작 세기가 되고, 코드는 "각 동작이 어떻게 생겼는가"(ARKit 52개 계수)와 부위별 속도·립싱크 우선순위만 맡는다. 사용자 발화 구간에는 같은 질문을 `role: listening` 으로 물어 듣는 반응을 받는다. 정의는 `apps/offline-lab/src/shared/regions.ts`. 아래 5.3~5.5 의 기존 내용은 비교용으로 남긴다.
>
> 샘플 대화 22구간 첫 실행: 지연 p50 218ms, p95 393ms(동시 4건). 선택은 대체로 그럴듯했다.
>
> 같은 날 추가: 듣는 구간은 질문 문구와 선택지 설명을 듣는 사람 기준으로 따로 보낸다. 평범한 대화(여행 계획, 36구간)에서는 AI 구간 24개 중 21개, 사용자 구간 12개 중 10개가 다섯 부위 이상 기본 선택지로 나와, 감정이 없는 말에는 얼굴이 쉬는 것을 확인했다. 감정이 뚜렷한 샘플에서 무표정이 없었던 것은 대본 탓이었다. 같은 표정이 이어질 때 인위적으로 변화를 주는 처리는 넣지 않기로 했다(사용자 결정). 남은 확인: ARKit 모델에서의 생김새, 실제 대화 음성.

| ID | 타입 | 질문 내용 |
|---|---|---|
| valence | Score 5 | `current`에서 화자가 표현하는 정서: 매우 부정 ~ 매우 긍정 |
| arousal | Score 5 | `current`의 에너지: 매우 차분 ~ 매우 들뜸 |
| apologetic | Noul | 사과하거나 유감을 표하는 중인가 |
| empathetic | Noul | 상대의 어려움에 공감·위로하는 중인가 |
| playful | Noul | 농담하거나 장난스러운가 |
| surprised | Noul | 놀라움을 표현하는가 |
| emphatic | Noul | 무언가를 강하게 단언·강조하는가 |
| asking | Noul | 상대에게 질문하는 중인가 |
| uncertain | Noul | 확신이 없거나 망설이는가 |

**불확실성 처리**
- Score: `confidence`와 확률 분포의 퍼짐을 함께 써서 가중치를 만든다.
- Noul: confidence가 없으므로 확률 자체를 강도로 쓴다. 0.5 근처는 무시 구간으로 두고, 구간 폭은 Phase 0 데이터로 정한다(초기값 0.35~0.65).

### 5.4 코드 측 얼굴 매핑 (예시, 튜닝 대상)

| 판단값 | 주요 blendshape |
|---|---|
| valence + | mouthSmile_L/R, cheekSquint_L/R |
| valence − | mouthFrown_L/R, browInnerUp(소량) |
| arousal + | eyeWide_L/R(소량), browOuterUp, 머리 움직임 진폭·속도 증가 |
| arousal − | eyeSquint(소량), 머리 움직임 감소, 깜빡임 느리게 |
| apologetic | browInnerUp, mouthPress, 고개 약간 숙임 |
| empathetic | browInnerUp(약), 부드러운 미소(약), 느린 끄덕임 |
| playful | 비대칭 미소, 눈 약간 가늘게 |
| surprised | browInnerUp + browOuterUp, eyeWide, jawOpen(소량) |
| emphatic | 구간 시작 시 눈썹 순간 상승 + 고개 끄덕임 1회 |
| asking | 문장 끝에서 고개 기울임 + 눈썹 상승 |
| uncertain | 시선 옆으로, 입술 다묾, 고개 약간 기울임 |

- 매핑 테이블과 강도 계수는 설정 파일로 분리해 성격 프리셋으로 교체 가능하게 한다.

### 5.5 사용자 발화 반응 매핑

| 사용자 판단 | AI 반응 표정 | 다음 응답의 시작 표정 |
|---|---|---|
| valence − / 어려움 토로 | empathetic 상승, 느린 끄덕임 | 공감 표정 유지 |
| valence + / 좋은 소식 | 미소, 눈썹 상승 | 미소 |
| surprised | 약하게 따라 놀람 | 눈썹 약간 상승 |
| asking | 집중: 시선 고정, 눈썹 약간 상승 | 중립에 가까운 "말 시작" |
| playful | 미소 | 미소 |

### 5.6 분석기 선택과 대조군
- Jev는 기본 분석기 후보이지 확정이 아니다. Phase 0에서 **같은 질문 세트를 소형 LLM(구조화 출력)에도 던져** 판단 품질, 지연, 비용을 나란히 비교한다.
- 텍스트를 제어할 수 있는 API 경로에서는 **인라인 감정 태그**가 세 번째 후보다(추가 호출 없음).
- 분석기 인터페이스는 `구간 텍스트 + 맥락 → 판단값 묶음`으로 고정하고, 세 구현을 모두 이 인터페이스 뒤에 둔다.
- Jev 약점 대응: 카운팅·산술·날짜 판단은 시키지 않는다. 한국어 품질이 부족하면 질문 지시문 영어화를 먼저 시도한다.

## 6. 사용자 발화 전사와 개인정보

### 전사
- OpenAI Realtime의 입력 전사는 사용자가 말을 마친 뒤 도착하는 것으로 보인다. Phase 0에서 확정한다.
- 발화 중 부분 전사가 오지 않으면 마이크 스트림을 별도 스트리밍 STT에 병렬로 보낸다. 후보 2~3개를 한국어 부분 전사의 지연과 품질로 비교한다.
- 2단계 옵션: 음성 감정 점수(Hume 등)를 사용자 반응 입력에 추가할 수 있게 인터페이스를 열어 둔다.

### 개인정보 (v4 신설)
- L1에서는 AI 발화 텍스트가, L2에서는 **사용자 발화 음성과 텍스트**가 분석기·STT 업체로 전송된다.
- 데모: 시작 화면에 전송 대상과 목적을 고지하고 동의를 받는다.
- 서버 프록시 로그는 기본적으로 본문을 저장하지 않는다. 디버그 모드에서만 저장하고 보존 기간을 둔다.
- 녹화 하네스 파일은 로컬에만 저장하며, 공유 전 사용자 음성 구간을 제거하는 옵션을 둔다.
- 배포 가이드: 각 수준에서 어떤 데이터가 어디로 나가는지 표로 안내하고, 각 업체의 데이터 보존 정책 확인을 도입자의 책임으로 명시한다.

## 7. 표정 엔진 세부

### 7.1 목표값의 두 종류
- **예약 목표값**: AI 발화 구간의 분석 결과. 재생 시각에 활성화.
- **즉시 목표값**: 사용자 반응, 시작 표정, 턴 상태 전환, 끼어들기. 도착 즉시 활성화.

### 7.2 레이어 합성 순서 (매 프레임)
1. **idle**: 중립 + 호흡, 미세 머리 흔들림
2. **턴 상태**
   - listening: 시선 정면, 주기적 가벼운 끄덕임, 눈썹 약간 상승
   - thinking: 시선 위·옆으로 잠깐, 입 다묾
   - speaking: 립싱크 활성, 머리 움직임 증가
   - idle: 시선 가끔 이동, 깜빡임 주기 길게
3. **감정·의도**: 5.4 매핑 → EMA 보간(시간 상수 150~300ms) → 감쇠(새 판단 없으면 3~5초에 걸쳐 중립)
4. **립싱크**: viseme 가중치. 입 영역 충돌 시 립싱크 우선, 미소는 입꼬리만 남긴다.
5. **절차적 오버레이**: 깜빡임, 발화 시작 눈썹 상승, 문장 끝 끄덕임

### 7.3 안정화 장치
- 히스테리시스, 불확실성 가중, slew rate
- 충돌 규칙: 예) valence − 와 playful이 동시에 높으면 쓴웃음 프리셋

### 7.4 수준 강등
- 분석기 요청이 연속 실패하거나 지연이 임계값을 넘으면 감정 레이어를 감쇠시키고 L0로 동작한다. 복구되면 자동으로 올라간다.
- STT가 끊기면 L2 반응만 끄고 L1은 유지한다.
- 현재 수준은 이벤트로 외부에 알린다(디버그 패널 표시, 도입자 로깅용).

## 10. 개발 단계 (총 10주, 수직 우선)

### Phase 0 — 가설과 전제 검증 (2주)

**0-A. 오프라인 최선 조건 실험 (첫 주, 가장 먼저)**
목표: "텍스트 의미로 만든 표정이 보기에 좋은가"를 실시간 제약 없이 확인
- [ ] 2~3분짜리 음성 대화 1~2개 녹음 (AI 음성 + 사용자 음성 + 텍스트)
- [ ] 오프라인 음성 인식으로 단어 타임스탬프 추출 → 완벽한 정렬 확보
- [ ] 절 단위로 5.3 질문 세트 실행 (Jev, 소형 LLM 각각)
- [ ] 5.4 매핑 초안 + 최소 엔진(보간, 깜빡임, 립싱크)으로 VRM 영상 렌더
- [ ] 세 가지 영상 제작: L0만 / L1 / L1 + 듣기 반응
- [ ] 3~5명에게 순서를 섞어 보여 주고 선호와 어색한 순간 수집
- **판정**: L1 영상이 L0보다 과반 선호되면 진행. 아니면 매핑·질문을 고쳐 1회 재시도, 그래도 아니면 방향 재검토(L0 중심 제품 또는 오디오 기반 도구 결합).

**0-B. 실시간 전제 측정 (둘째 주)**
- [ ] 전송 방식: WebSocket과 WebRTC 각각에서 텍스트 선행 시간 분포, 재생 위치 파악 가능 여부, 4.2 추정 방식별 표정 시각 오차 측정
- [ ] 사용자 입력 전사가 발화 중에 오는지 확인, 스트리밍 STT 2~3개 비교
- [ ] 분석기: Jev와 소형 LLM의 판단 품질(0-A 평가 재사용), 한국발 지연 p50/p95(프록시 리전별), Jev rate limit 실측
- [ ] 음성별 말하기 속도 평균 측정
- **결정 사항**: 전송 방식, 기본 분석기, STT, 프록시 리전, 질문 지시문 언어

### Phase 1 — 수직 관통 (2주)

> **2026-11-12 진행 상황.** 첫 구현을 만들었다: `apps/realtime`(OpenAI Realtime, WebRTC)와 `packages/core`(오프라인 도구와 함께 쓰는 엔진). 범위 결정: 판매하지 않고 오픈소스로 공개, 표정은 텍스트만으로 정함(오디오 감정 분석 제외, 립싱크만 오디오 사용), 얼굴은 코드로 그린 로봇·강아지. 모의 대화(사건 순서만 흉내, Jev 는 실제 호출)에서 9개 절 모두 제때 걸렸고 Jev 응답은 평균 270ms 였다. 실제 OpenAI 연결은 키가 없어 아직 실행하지 못했다. 남은 것: 실제 연결 확인과 시점 실측, 시작 표정 선점, 말하는 도중의 듣는 반응.
목표: 2주 뒤 실제 음성 대화에서 얼굴이 움직인다. 거칠어도 전체 경로가 연결된 상태.
- [ ] `adapter-openai-realtime`: 결정된 전송 방식으로 연결, 공통 이벤트 변환
- [ ] `lipsync-webaudio` + `renderer-vrm`: 립싱크와 렌더링
- [ ] `core`: 60fps 루프, 레이어 합성, 턴 상태, 깜빡임 → **L0 완성**
- [ ] `apps/server`: 임시 토큰, 분석기 프록시
- [ ] `analyzer-*` + AI 발화 큐 + 단순 타임라인(말하기 속도 고정값) → **L1 초안**
- [ ] 0-A의 최소 엔진과 매핑을 그대로 이식
- 완료 기준: 5분 대화가 끊김 없이 돌고, L0와 L1을 토글로 비교 가능

### Phase 2 — 타임라인 정밀화와 도구 (2.5주)
- [ ] 진행형 타임라인: 쉼 보정, 앵커, 속도 갱신, 예약 재계산
- [ ] 시작 표정 선점, 끼어들기 취소
- [ ] 안정화: EMA·히스테리시스·slew·감쇠·충돌 규칙, 수준 강등
- [ ] 녹화·재생 하네스, 오차 자동 측정(4.5), 디버그 패널
- 완료 기준: 표정 시각 오차 p95 목표 충족, 녹화 세션 재생으로 동일 결과 재현

### Phase 3 — 듣기 반응과 튜닝 (2주)
- [ ] STT 연결, 사용자 발화 큐, 반응 매핑 → **L2 완성**
- [ ] 개인정보 고지 화면, 프록시 로그 정책
- [ ] 10세션 녹화 → 재생 기반 튜닝, 표정 변화 빈도 등 지표 목표치 확정
- [ ] 사용자 평가 1차 (5명 이상)
- 완료 기준: 사용자 반응 지연 p95 1초 이내, 평가에서 L2가 L1보다 "듣고 있다" 항목 우세

### Phase 4 — 두 번째 어댑터와 패키징 (1.5주)
- [ ] `adapter-claude-tts`: Claude SSE + Azure TTS (단어 타임스탬프 경로 검증), 인라인 태그 분석기
- [ ] 성격 프리셋, 반응 매핑 설정 API
- [ ] npm 배포, README, 수준별 최소 예제(L0는 키 없이 동작), 서버 배포 가이드, 데이터 흐름표
- [ ] 외부 렌더러 연동 가이드 (Live2D, Unity WebGL)

## 11. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 의미 기반 표정이 기대만큼 좋아 보이지 않음 | Phase 0-A에서 첫 주에 확인. 판정 기준과 재검토 경로 명시 |
| 타임라인 추정 오차 | 전송 방식 비교 후 선택, 쉼 보정, 오차 자동 측정, 단어 타임스탬프 경로 우선 |
| 응답 첫 구절 표정 공백 | 시작 표정 선점, 첫 구간 조기 분할 |
| 사용자 발화 중 전사를 못 받음 | 별도 STT. 지연이 크면 L2를 음성 에너지 기반 절차적 반응으로 대체 |
| 분석기 품질·지연 부족 | 대조군 비교로 선택, 인터페이스 뒤에서 교체 가능 |
| rate limit / 과부하 | 전역 동시 상한, 사용자 큐 우선, 수준 강등 |
| 표정 과잉·산만함 | 히스테리시스, slew rate, 무시 구간, 프리셋 강도 계수 |
| 도입 장벽 (외부 키 4종) | L0는 키 없이 동작, 수준별 점진 도입 |
| Jev 서비스 의존 | 분석기 추상화, LLM·인라인 태그 대체 구현 유지 |
| 개인정보 | 고지·동의, 로그 최소화, 데이터 흐름표 |
| 불쾌한 골짜기 | 스타일화된 VRM으로 시작 |

## 13. 미결 사항 (모두 Phase 0에서 결정)

- 전송 방식: WebSocket vs WebRTC
- 기본 분석기: Jev vs 소형 LLM
- 질문 지시문 언어, STT 선정, 프록시 리전
- 첫 데모 아바타 (이용 조건 확인 포함). **ARKit 52 blendshape 를 가진 VRM 이어야 한다.** 오프라인 실험 도구를 만들며 확인한 바, 일반 VRM 은 표준 표정 몇 개만 가져서 엔진 출력의 대부분이 뭉개진다. 표준 표정 모델용 대체 경로는 `apps/offline-lab/src/viewer/rig-vrm.ts` 에 있으나 실험과 데모에는 부적합하다.
- 패키지 관리자: 계획은 pnpm 이었으나 개발 환경에 없어 npm workspaces 로 시작했다. 구조는 같으므로 필요하면 나중에 옮긴다.
- Audio2Face 계열 립싱크 결합 여부: Phase 3 이후 판단
